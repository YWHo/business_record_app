# Security and reliability review

Review date: 2026-09-13

Scope: Phase 20 review plus the version 2 public-demo cost/abuse addendum covering the React PWA, Cloudflare Worker, D1, private R2 storage, local/demo/production configuration, portable exports, retention workflow, and resolved dependency graph.

## Review outcome

The application keeps authorization and validation at the Worker boundary and has no public production signup path. Phase 20 closed the concrete gaps found during review: deployed unsafe requests now require the configured origin; rate limiting covers client and stable-subject dimensions; uploads and exports have a dedicated low-volume limiter; unauthorized upload streams are discarded incrementally without buffering their bodies; remote security-provider calls are time-bounded and fail closed; the email relay must use HTTPS; security headers cover static and API responses; URL tokens are removed from browser history after capture; textual CSV formula prefixes are neutralized; demo bootstrap is unreachable; and the resolved dependency graph has no known advisories at the configured threshold. The version 2 addendum further makes the public demo read-mostly, rejects upload/export/purge work server-side, applies dedicated global demo read/write limits before route handling, paginates high-cardinality reads, caps collection responses, caches hashed assets, and adds automated binding-separation and destructive-reset checks.

## Threat model

Protected assets are financial records, identity and role state, immutable source documents, audit history, retention settings, export archives, login/invitation/session tokens, deployment secrets, and service availability. Trust crosses from an untrusted browser into the Worker, from the Worker into D1/R2 bindings, and from the Worker to Turnstile and the configured email relay.

Relevant attackers include an unauthenticated internet client, an authenticated accountant attempting owner actions, a user submitting hostile text or files, an automated client abusing login/invitation or expensive endpoints, and a reader of the public source code. Cloudflare account compromise, a compromised email inbox, malicious platform administrators, and endpoint malware are outside what application code alone can prevent and require operational controls.

## Control review

| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authorization                        | Reviewed every registered route. Only health, auth configuration, login/verification, invitation acceptance, guarded demo auth, and guarded bootstrap are unauthenticated. Reads require an active session. Source/reference mutations and destructive governance actions are owner-only; explicitly designed accountant writes remain constrained to review, comments, reconciliation, saved views, and attributed insurance allocation. Demo account administration and bootstrap are blocked.   | Re-run the route inventory whenever an endpoint or role is added. Frontend visibility is convenience only.                                                                                                    |
| Login and invitation abuse           | Login responses do not enumerate accounts. Login and invitation tokens are high-entropy, hashed at rest, expiring, and atomically single-use. Invitation acceptance binds token to the exact normalized email and cannot transfer ownership. Disabled accounts cannot authenticate and lose sessions. Magic tokens are removed from browser history immediately after capture.                                                                                                                     | Email-account security remains part of the authentication boundary. Configure short email-link retention and avoid mail-provider click rewriting where it consumes one-time links.                            |
| DDoS and rate limiting               | Auth, bootstrap, invitation, demo login, upload, and export paths use named Cloudflare rate-limit bindings. Keys are SHA-256 values derived separately from the Cloudflare client address and stable subject where available. The demo adds separate read/write limits before route work and fails closed if either binding is absent. Oversized declared JSON/upload bodies fail early, and unauthorized upload streams are discarded incrementally with a 27 MB ceiling and no aggregate buffer. | Worker rate limiting is permissive, eventually consistent, and location-scoped. Configure account-level Cloudflare DDoS/WAF rules, usage/budget notifications, and alerts; tune thresholds from observations. |
| Turnstile and challenge verification | Production login requires a token. Server verification sends the secret directly to Cloudflare, supplies remote IP and an idempotency key, and requires success plus the exact `login` action and configured hostname. Calls time out and fail closed. Turnstile is not added to invitation acceptance because the unguessable single-use invitation token plus exact email and limiter are the authorization factors; bootstrap similarly requires its secret.                                    | Bind the production Turnstile widget to the final hostname and keep the secret only in Wrangler secrets. Reassess challenges if anonymous sensitive forms are added.                                          |
| Uploads                              | The public demo rejects uploads and incrementally consumes the request stream before authentication, D1, R2, parsing, or hashing. Elsewhere, owner authorization happens before body parsing; requests have a 27 MB envelope check and files a 25 MB byte check. Only JPEG, PNG, WebP, and PDF signatures matching declared MIME are accepted. Keys are server-generated, R2 is private, and D1 failure triggers best-effort cleanup.                                                              | Signature checks are not malware detection and polyglot files remain possible. Add quarantine/content scanning before broadening beyond trusted invited users; retain Cloudflare request-size limits.         |
| Secrets and public source            | Git ignore rules exclude `.dev.vars`, general `.env` files, Wrangler state, builds, reports, and generated bindings; committed mode files contain only environment selectors. Repository scanning found only documented placeholders and synthetic identities. D1/R2 access uses bindings, not embedded credentials. Production bootstrap, Turnstile, and relay credentials are Wrangler secrets. Public routes do not rely on obscurity.                                                          | Enable repository secret scanning and protected deployment environments. Rotate immediately if a real value enters source history. Replace resource/origin placeholders before deployment.                    |
| Browser/API policy                   | Static assets and API responses deny framing and sniffing, send no-referrer and restrictive permissions policies, and use CSP compatible with Cloudflare Turnstile. Deployed responses enable HSTS. API JSON and private downloads are non-cacheable. Deployed state-changing requests require exact `APP_ORIGIN`; the GET-based streaming export additionally requires same-origin Fetch Metadata. Strict same-site cookies remain defense in depth.                                              | Keep CSP allow-lists narrow when adding third-party assets. A changed hostname must update `APP_ORIGIN`, Turnstile hostname settings, and deployment configuration together.                                  |
| Logging                              | Expected client errors return bounded messages without internal details. Unexpected errors log only request ID, environment, method, and pathname; the response carries the request ID for correlation. Tokens, request bodies, filenames, emails, secrets, and stack traces are not intentionally logged. Audit events store actor/action/entity and bounded summaries rather than credentials or document contents.                                                                              | Enable Workers Logs with access controls, sampling, retention limits, 429/5xx alerts, and no request-body logging. Treat log exports as sensitive operational data.                                           |
| Retention and deletion               | The demo rejects permanent purge before database or object operations. Elsewhere, policy validation enforces at least seven tax years and valid calendar boundaries. Existing dates are never shortened. Purge requires owner role, trash state, elapsed eligibility, exact confirmation, and no live fuel reference. Cross-store purge is marked pending before R2 deletion and is retryable; immutable actor-attributed audit remains.                                                           | Purge is manual. Operators should periodically review eligible records, interrupted purges, demo bucket cleanup, and applicable NZ/legal retention obligations.                                               |
| Export integrity                     | The demo rejects dynamic archive generation before authentication or source reads. Elsewhere, scope and dates are validated; counts are reconciled; every R2 object is preflighted; source/generated bytes are hashed; paths are sanitized; ZIP bounds/CRC are checked; and the manifest digest is stored in D1. Exports never mutate sources, and textual CSV formula prefixes are neutralized.                                                                                                   | Version 1 has no importer. Verify manifest hashes before use and perform future restores in an isolated environment. Protect downloaded archives outside the application.                                     |
| Dependencies                         | `pnpm audit --audit-level moderate` initially found a high-severity `sharp` advisory through development-only Miniflare. Updating the Cloudflare Vite plugin, Workers types, and Wrangler resolved `sharp` 0.35.4; the repeated audit reports no known vulnerabilities. Exact resolutions remain in `pnpm-lock.yaml`.                                                                                                                                                                              | Run `pnpm security:audit` in CI, use `pnpm install --frozen-lockfile`, review update provenance, and patch supported releases promptly.                                                                       |

## Deployment gate

Before production release, replace every placeholder binding/origin, set all documented Wrangler secrets, bind Turnstile to the exact public hostname, keep R2 private, apply migrations to the explicitly named environment, configure WAF/DDoS and observability alerts, verify response headers and origin rejection, run the dependency audit and full automated suite, create and verify a complete export, and rehearse recovery in an isolated environment. Phase 21 turns this gate into the final deployment and recovery runbook.

For the demo, keep the Free plan unless a later review deliberately changes it; confirm demo/production binding separation; verify the read/write limiters; leave upload, archive, email, and purge disabled; keep only synthetic data; periodically inspect Workers/D1/R2 usage and 429/5xx trends; and treat budget alerts as notifications rather than hard caps. Static hashed assets are cached immutably and the application shell does not require D1 or R2.
